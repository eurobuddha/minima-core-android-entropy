Entropy RNG Audit

Are the seed-phrase dice rolls truly random, or crackable? A full-path review of the roll engine, BIP39 encoding, and IPC transport in the Entropy native Android app for Minima.

⚄⚄

Verdict: cryptographically sound — not crackable in any practical sense. Every roll mixes a fresh 256-bit kernel-CSPRNG secret with independent node randomness through SHA3, with exact rejection sampling. An attacker faces 2128–2256 uniform possibilities and no computational shortcut. The weak-PRNG failure class behind the wallet-drain hacks does not exist in this design.

⚀How one die face is made

RollEngine.java — ported from the Zero Edge Casino resolve maths, proven on-chain.

  1. aThe Minima node supplies fresh randomness via its random command. First independent CSPRNG. Travels over package-targeted IPC only.
  2. bThe device draws a fresh 32-byte secret from SecureRandom — per roll. Second independent source: the Android kernel CSPRNG. 256 bits nobody else ever sees in advance.
  3. hThe node computes SHA3(a ++ b) — bit-identical to the KISS VM script, so any roll can be re-verified with runscript in a Minima terminal. Either source alone failing still leaves the output unpredictable.
  4. nThe first 4 bytes of the hash become a 32-bit number; values ≥ 4294967292 are rerolled. 4294967292 = floor(2³²⁄6)·6 — rejection sampling gives every face exactly 1⁄6. Zero modulo bias, pinned by a unit test.
  5. ⚅n mod 6 + 1 is the face. Faces become entropy bits via the iancoleman unbiased encoding, locked to the genuine bip39 code by fixed vectors. Bip39Test verifies parity with iancoleman/bip39 v0.4.3; generation is blocked if the self-test fails.

⚁Why the known wallet-RNG hacks don't apply

Every drained-wallet RNG incident shared one root cause: a small, enumerable seed space.

Those wallets asked a non-cryptographic generator, seeded with a handful of guessable bits, to invent the whole seed — so attackers simply enumerated every possible seed and swept the matching addresses. Entropy has no such shortcut: even an adversary who fully controls the node's contribution still faces the 256-bit device secret behind SHA3.

⚃Residual risks — and the hardening shipped

None is a practical crack; all assume a compromised device or misused demo mode. All three were addressed the same day.

The node can reconstruct the seed

The SHA3 runs on the node, so Minima Core sees both secrets and hence every face. This is the deliberate price of on-chain verifiability — and if Minima Core or the phone is compromised, any on-device generator has already lost. The per-roll audit log is equally seed-equivalent.

0.1.8 adds a warning above the audit log: treat it exactly like the seed words.

Demo mode lifts FLAG_SECURE

Demo mode (0.1.7) makes the screen capturable for presentations. Faces captured on a mirrored or recorded screen are seed material.

0.1.8 blocks all rolls — digital and physical — while demo mode is on, and re-blurs any revealed words the moment it is switched on.

IPC auth tokens came from java.util.Random

The tokens authenticating node replies to the app's exported receiver were minted by a 48-bit-seeded, non-cryptographic PRNG. Blind forgery over broadcasts was already infeasible, but the barrier was thinner than it should be.

The shared minimaapi SDK now mints all IPC tokens with SecureRandom; the rebuilt library ships inside 0.1.8.

⚄Digital rolls vs five physical dice

For every purpose that matters to a seed phrase: yes — at least as random, and in one respect better. The guarantees differ in kind, not in practical strength.

digital wins: exactness

  • Rejection sampling makes every face exactly 1⁄6 — no physical die achieves that.
  • Household dice have rounded corners, off-center pips, thrower habits — measurable bias that shaves entropy per roll.
  • Computationally indistinguishable from perfect dice to any adversary who can't break SHA3 or the kernel CSPRNG.

physical wins: unconditional physics

  • A fair die rolled unobserved is unpredictable by physics alone — no cryptographic assumptions.
  • Malware can't touch a die on the table…
  • …but in this app the physical faces are typed into the same phone, so a compromised device reads those too. Physical mode only truly wins with the whole derivation done off-device.

On an uncompromised phone, the digital rolls are at least as strong as ideal dice and stronger than typical real ones. The one scenario where physical dice genuinely win — a fully compromised device — is one where any app has already lost, whichever mode is used.
